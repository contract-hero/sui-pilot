Formal verification for Move — the Sui Prover investigation.

How sui-pilot grew a formal-verification capability: a /specify skill that authors #[spec(prove)] specifications, a /verify skill that re-checks them against drifting code, an MCP server that wraps the sui-prover binary, and a bundled prover-docs corpus — hardened by a live evaluation against a production AMM. This page is the candid record: what shipped, what the eval exposed, and what is still open.

What ships today Try it The live eval

Why formal verification, and what the Sui Prover is

Tests sample behavior; a prover exhausts it. For Move packages guarding real value, a machine-checked proof that a property holds on every input is a different class of assurance than a green test suite.

The Sui Prover (by Asymptotic) verifies Sui Move code against specifications written as ordinary Move functions annotated with #[spec(prove)], using requires, ensures, asserts, and the macros clone!, forall!, exists!, and invariant!. It installs with brew install asymptotic-code/sui-prover/sui-prover and relies on the implicit framework dependencies of Sui 1.45+, so a Move.toml that pins Sui or MoveStdlib explicitly has to drop those entries first.

Crucially, this is not the legacy Move Prover's MSL. The old syntax an LLM remembers from training — aborts_if, pragma, apply, assume, free axiom — is not what the Sui Prover uses. That is exactly the failure mode sui-pilot exists to fix, so the plugin bundles .sui-prover-docs/ as the sixth of its doc corpora (800+ docs across all six), synced from Asymptotic's upstream repos:

sources/ prover.move · ghost.move · log.move · vector.move

The construct definitions specs import via #[spec_only] use prover::...: native requires/ensures/asserts, Boogie tuning hooks, ghost global state.

Four waves in two weeks

The capability landed and matured in four waves over roughly two weeks in May 2026. Three are in git history (PRs #24 and #27, #30, #32); one is a design note that lives outside the repo.

1

The big-bang landing — 2026-05-14 (PR #24)

A single squashed PR delivered the whole stack in four planned phases: the .sui-prover-docs/ corpus, the sui-prover-mcp server with three tools, the /specify command + skill (specs persisted inline in the user's .move files at that point), and a non-interactive mode with a discovery eval. The same afternoon, a live /specify run against Aftermath Finance's public AMM surfaced 12 findings (3 BUG, 6 GAP, 3 UX) — all fixed the same day in PR #27.

A design pass explored splitting the capability in two: /specify for spec authoring, /verify for re-checking. Five design questions — report granularity, living-vs-snapshot reports, source rendering, verification-context binding, and narrative structure — were resolved and locked. The note itself is not in git; the skills cite its Q and L labels.

3

The same PR added skills/verify/SKILL.md — the read-mostly consumer half of the split, with drift detection and verdict buckets.

4

Polish — 2026-05-25 (PR #32)

Pre-sharing cleanup registered /verify as a slash command (commands/verify.md), added it to the README and landing-page command tables, added the sui-prover-mcp build step to the README, and refreshed the per-corpus doc counts.

What ships today

One dedicated MCP server (the skills also call three move-lsp tools), one bundled docs corpus, and two of sui-pilot's five skills, with an explicit boundary between them: /specify authors; /verify checks. The other three skills — /oz-math, /sui-setup, /sui-e2e — are outside the FV workflow.

Skill

/specify — the producer

An interactive, multi-phase orchestrator that authors #[spec(prove)] specs for every externally reachable function (public non-package plus entry) of a Sui Move package. It ends with a spec-context.json manifest and an invariant-driven HTML report.

Interactive by default; SPECIFY_AUTO_DEFAULTS=1 or an explicit “don't stop” directive switches to non-interactive mode, which picks defaults and caps iterations at one.

Skill

/verify — the consumer

Read-mostly: it never authors, edits, or deletes a spec, and never edits a Move.toml. It reads the manifest, detects drift, re-runs the prover on every spec package with its recorded flags, and reports which guarantees still hold. Uncovered functions get routed back to /specify.

Flags: --strict, --report <path> (default .verify-report.html), --package <name>.

MCP server

sui-prover-mcp

A TypeScript wrapper around the sui-prover binary that exposes exactly three tools: prove_package, list_specs, prover_capabilities. By design it never edits the user's Move.toml — setup issues surface as setup_warning findings.

The load-bearing decision: specs live in a sibling package

Verification scaffolding never touches deployed source. Specs land in a separate <pkg>_specs/ package of #[spec(prove, target = ...)] twin functions — one <mod>_specs.move per source module — leaving the production package with no #[spec_only], no prover dependency, no marker blocks. Inline emission remains available as an --inline opt-out. Functions that need a non-default prover invocation (e.g. --no-bv-int-encoding for bit-exact semantics) move to a lazily created second <pkg>_specs_bv/ package with its own recorded flag set.

The /specify phases

PhaseWhat happens
0 · ValidateHard gate: prover_capabilities probe, a compile-health check via move_diagnostics, a git ls-remote reachability check on every git dependency, and setup warnings. A missing binary stops an interactive run with the brew command; a non-interactive run falls back to discovery only.
1 · DiscoverComment-aware regex over sources/ finds the public + entry surface; the skill uses list_specs to mark each function verified, pending, or partial; progress goes to .specify-progress.json.
1.5 · Scope + calleesAbove 25 functions, ask how to scope. Flag stub callee modules (every body abort 0 or native) that would make proofs vacuous.
2 · CascadePer function: callers via move_find_references, callees via move_goto_definition, depth 2 by default.
3 · Prioritizeentry first, then mutating public functions, then read-only ones.
3.5 · ScaffoldCreate the sibling <pkg>_specs/ package (skipped under --inline).
4 · Per-function loopSurface a fact sheet → elicit abort conditions first, then postconditions, preconditions, invariants → draft → review → persist → prove → diagnose via the failure taxonomy → iterate (up to 3 attempts by default).
5 · Hand offWrite spec-context.json and the report; under --audit, add counterexample regressions and a prover.yml CI stub; point the user at /verify.

MCP tool surface

ToolInputsOutput and design choices
prove_package path (package dir or a .move file; walks up to Move.toml), target_function or target_module, timeout_seconds (per spec, default 60), verbose, extra_args. Spawns the binary shell-free. Returns a typed summary.overall (verified_all / failed_some / no_specs / compile_failure / timeout / error) with verified/failed/skipped/timeout counts, plus findings[] tagged with 19 kinds. Unknown extra_args flags are dropped with a warning, never forwarded; raw output is ANSI-stripped and truncated to head + tail on compile failures.
list_specs path (package dir, .move file, or sources/). Comment-aware regex scan for #[spec(...)] functions: file, line, name, target, attributes. Exists because the binary has no “list existing specs” command; /specify uses it for idempotency and resume, /verify to cross-check the manifest.
prover_capabilities move_toml_path (optional). Reports binary presence, version, and sui_prover_flags (parsed from --help), cloud config, Sui toolchain version, per-package setup warnings (explicit framework deps, non-2024 edition), and declared git dependencies. Reachability of those deps is left to the caller.
per-spec verdicts verified · failed · skipped · timeout
pre-spec compile failures dep_address_conflict · unresolved_named_address · unresolved_module · dep_fetch_failure · function_not_found · spec_target_body_no_call · no_specs_to_prove
legacy / generic ensures_failed · asserts_failed · abort_unspecified · no_spec · parse_error · compile_error · setup_warning · unknown

The 19 finding kinds, from mcp/sui-prover-mcp/src/parse-output.ts. Each one maps to a repair recipe in skills/specify/references/failure-taxonomy.md.

Two details worth knowing

Discovery is regex, not LSP: move_document_symbols returns every function as kind: 'function' with no visibility, so Phase 1 runs comment-aware regex over the source to find the public/entry surface. And stub or external callees are axiomatized with #[spec(skip, target = ...)] functions in a <pkg>_specs/sources/specify_axioms.move sidecar — every such axiom is trusted, not proved. Each one, plus any hand-written Boogie axiom loaded via extra_bpl, is disclosed in the report's “Trusted axioms — not proved” section.

Toolchain status, 2026-09-28

A cold eval of /specify and /verify on 2026-09-28 (issue #31) found that the default install cannot produce a verified spec. The brew bottle (built 2026-05-28; sui-prover --version prints 1.5.3) fetches its runtime dependencies from moving branches: asymptotic-code/sui-prover main and asymptotic-code/sui next. Upstream changed the spec syntax on 2026-09-18. With those branches at their 2026-09-25 heads, a toy spec fails with 42 restricted visibility errors, and /specify Phase 0 does not detect it. Until the bottle and the upstream branches agree again, steps 2 and 3 do not end in a verified spec.

The producer/consumer split

A proof is only meaningful while it is about the current code. The split exists to make that binding explicit and checkable.

“A spec is a claim of the form ‘this code, at this state, against these deps, satisfies this property.’ /verify's job is to answer ‘is that claim still true, and is it still about the current code?’”
skills/verify/SKILL.md
Binding

spec-context.json

/specify ends every run by writing a reproducibility manifest: per-function source hashes keyed <mod>::<fn>, spec packages with their prover flags, dependency pins, and toolchain versions (sui-prover, Sui CLI, Boogie, Z3).

The default hash recipe (normalized_source) strips comments, collapses whitespace, then keeps the first 16 hex chars of sha2-256 — so reformatting does not register as drift, but any token change does. A bytecode method is opt-in and needs a successful build.

Checking

Three drift axes, six verdicts

/verify detects source drift (recompute each hash with the exact recipe /specify used), coverage drift (re-run discovery; find uncovered new functions and orphaned specs), and context drift (toolchain versions and git-dep revs vs the manifest).

It then joins prover result with hash freshness into verdict buckets: holds, violated (fresh + failed = real regression), stale-passing, stale-failing, uncovered, orphaned. A violated verdict means you broke a property you committed to; an uncovered one means you entered territory the specs never described.

CI posture

Default mode is warn-and-run: exit zero unless a spec hard-fails to prove (failed_some, compile_failure, or error). /verify --strict is the CI contract — the skill specifies a non-zero exit on any spec failure, stale spec, uncovered function, missing spec package, or context drift (moved dep or changed prover version), because CI must catch “the proof is no longer about the current code,” not just “a spec failed.” A package with no specs at all exits zero even under --strict. The prover.yml stub that /specify --audit emits runs the prover once per spec package with its recorded flags. Without a manifest, /verify degrades honestly: it re-proves the spec packages and reports verdicts, but announces that drift detection is unavailable. The 2026-09-28 eval found that the --strict exit code is prose only: a headless --strict run reported a failure and still exited zero.

Empirical grounding: the Aftermath AMM eval

On 2026-05-14 — the day the stack landed — a live /specify run was observed against a real production codebase: Aftermath Finance's public AMM.

The target: 4 packages, 229 externally reachable public/entry functions, private git dependencies, and a stub-only utilities::fixed module whose every function body is abort 0. The method: a second Claude Code session in a sibling worktree armed a tail -F on the target session's transcript and a 5-second mtime poll on its files — non-intrusive observation, no edits to the target repo. Toolchain at the time of the run: sui-prover 1.5.3, sui 1.69.2. The run first stopped at a private-dependency blocker, then continued after Option B (a local clone of the private dependency) unblocked the build. Verdict: Conditional Pass

Outcome

47 verified specs

100% spec coverage of amm-math's externally reachable surface: 47 verified specs plus 22 callee axioms in a sidecar — 141 verification subchecks, 0 failures, 0 timeouts, on a real AMM math kernel covering weighted geometric mean and the Curve stable curve.

Caveat

ignore_abort everywhere

Every spec used ignore_abort — in the report's own words, “postcondition smoke tests, not full abort-safety proofs.” A follow-up pass removing it and adding precise abort conditions was flagged as the next step.

Findings

12 fixes, same day

3 BUGs, 6 GAPs, 3 UX items (plus 3 WINs) — all 12 fixed in PR #27 within hours: output-parser rewrite, summary.overall, structured failure kinds, a hard Phase 0 compile gate, a scope + callee-quality probe, and taxonomy docs.

The most critical finding

BUG-03: the MCP failed to parse successful prover output. A run with four checkmark verifications and a literal “Verification successful” line still returned summary {verified: 0, failed: 0, skipped: 0, timeouts: 0} and findings: [].

“Any agent or eval rig that trusts the summary will conclude the run did nothing — the exact opposite of the truth. … This is the single highest-leverage fix in the sui-prover-mcp surface — every other finding in this report becomes secondary if the structured output is wrong.”
evals/specify-aftermath-eval/report.html, BUG-03

The report's conclusion: the feature is conclusively workable on hard real-world Move code — the GAP/BUG/UX items were “friction in the surrounding tooling, not capability gaps.” The eval also caught things the skill spec never taught: the agent spotted the stub-callee vacuous-verification trap unprompted, and the blocked-state artifacts (a structured .specify-progress.json blocker record plus a self-contained HTML report) exceeded the documented contract.

This live-observation eval is distinct from the project's automated v1-vs-v2 A/B eval framework (27 tasks as documented, since grown to 32 in evals/tasks.json) — it was a one-off production-grade probe of the /specify deliverable itself, not a plugin-version comparison. The full write-up lives in the repo at evals/specify-aftermath-eval/report.html.

The deliverable redesign: five locked decisions

The design pass resolved five questions about what a formal-verification deliverable should be. Four of the five decisions (Q1, Q2, Q4, Q5) are visible in today's skills/specify/SKILL.md; Q3's source-rendering rule is not.

QuestionLocked decision
Q1 · Granularity Hybrid — a per-module report (<mod>.spec.html) next to each spec module, plus a package-level index.html for cross-module invariants and the coverage matrix; --single-file for tiny packages.
Q2 · Living vs. snapshot Structured sections via HTML comment markers — specify:auto:* zones regenerate every run, specify:human:* zones are preserved — on a strong opinionated template.
Q3 · Source rendering Proposed in the design note as a hybrid — signature + spec body inline, link out for full source, full source inline under --audit. not in SKILL.md
Q4 · Context binding v1 = manifest only (spec-context.json capturing source hashes, dep pins, toolchain versions). v2 = preflight dep clone. v3 = drift enforcement.
Q5 · Narrative structure Invariant-driven primary view + function-index appendix. Invariants get a human name and a stable slug (INV-supply-conservation), linked from the spec module via explicit // invariant: markers, each with Abort conditions, Threat model, and Proof obligations sections.

The implementation (PR #30) also folded in nine learnings from a real Sui-Prover engagement — the integer-library work from Asymptotic × Bluefin — including abort conditions as first-class output, math-domain modeling for custom integer types, defining-property postconditions, per-package prover flags, and --audit regression artifacts with a prover.yml CI stub. Q4's v1 shipped as designed, and SKILL.md still lists v2 and v3 as roadmap. /verify --strict defines the drift checks, but the CI stub runs sui-prover once per spec package and does not compare source hashes, so CI alone does not catch a stale spec that still passes.
